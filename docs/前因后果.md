# 前因后果

记录文图方案（Doc-image-deck）从一次性脚本到可安装 skill 的过程、每一步做过的决定，以及验证数据。公开版本隐去了客户名称和客户材料。

## 一、起因：生图稿好看，但改不了字（2026-09-24）

一份通信行业客户的专项方案（23 页），改用 ChatGPT 的生图能力做：通过 Codex CLI 调用内置 `image_gen`，每页一次调用，文字、版式、配图一次生成，单页 1672 × 941。做法当天固定下来：

- 生图不画 Logo 和页码，这两样在合成时作为独立对象叠加，按角落明暗选深浅版本。
- 深色页以封面为风格参考、浅色页以第 2 页为风格参考，附图生成，保证全稿一致。
- 原稿里的 18 张截图不让模型重绘，按原比例合成进预留区。
- 用 macOS Vision 做 OCR，逐页核对生图文字。

成品是一页一张图，同事和客户没法改字。于是当天又试做了反向流程：识别文字、把文字从图上去掉得到底图、在原位置叠回可编辑文本框。第一版可编辑稿 23 页，文字与生图提示词逐条比对无缺漏，逐页平均色差 7.1–18.1（0–255 色阶）。

## 二、第一次完整验证：74 页整页图片提案（2026-09-24 至 09-25）

第二份材料是一份 74 页的珠宝品牌整合营销提案，每页一张 3840 × 2160 整页图片，宋体、黑体混排，有纸纹、烫金、深绿底。它不是本流程生成的，只有一份与成稿不完全一致的旧版文案和提示词可以对照。按同一方式还原，过程中解决的问题：

| 问题 | 处理 |
|---|---|
| PowerPoint for Mac 受沙盒限制，打不开新建目录里的文件（-9074 / 超时） | 把文件复制到 PowerPoint 自己的容器目录再打开、导出 |
| 同时开 3 个 LaMa 去字进程，16 GB 内存耗尽 | 最多 2 个进程；限制 Apple GPU 显存水位；大面积区域按遮罩最细处切块修补 |
| Vision OCR 常见误读：漏「的」，「的」读成「钓」「前」，「千」读成「干」 | 整页、1.0 倍裁切、1.6 倍裁切三路识别投票；旧版文案只能改识别结果有分歧的字 |
| 生图字形没有对应的字体文件 | 按笔画横竖粗细比判断宋体或黑体，按竖笔粗细选字重；同页同字号同颜色的行统一样式；字体用思源宋体、思源黑体 |
| 文本框位置对不齐 | 实测发现 PowerPoint 固定行距下，基线偏移只随行距变化，按 1 pt 台阶跳变；做成查找表，安装时标定 |
| 字距、空格、标点挤压、大小字混排 | 统一字距 + 空格额外间距 + 全角标点逐字实测挤压量 + 行尾小号 %、‰ 单独设字号 |

结果：1,631 行文字全部可编辑，与原稿逐页平均色差全稿均值 6.91。人工核对后写入替换表修正 95 行；页面措辞与旧版文案不一致的地方保留页面原文，列给使用者确认。

## 三、做成 skill：从文档一路到可编辑版（2026-09-25）

还原流程稳定后，往前补齐为完整流程，命名 image-deck-pipeline，Claude Code 与 Codex 共用一份文件：

1. 文档 → `outline.json` → 白板稿 PPTX：终稿文字加每页版面建议、配图建议，不做设计。
2. 3 个设计方向各出 2 张样张，使用者选定后全量生图，OCR 核对文字和 Logo、页码的预留角落。
3. 合成图文版 PPTX 与 PDF。
4. 以白板稿文字为准还原可编辑版。生图文字本来就取自白板稿，所以校字几乎不需要人工。
5. 清理中间文件。

用一份 4 页的诊断稿端到端测试：白板稿几秒；6 张样张约 3 分钟；4 页全量生图 77 秒，文字核对全部通过；可编辑还原 73 秒，32 条文案与白板稿逐字一致，逐页平均色差 8.0、13.3、5.9、5.5；清理后项目从 124 MB 降到 36 MB。测试中修正的问题：

- 按白板稿纠正识别结果时丢了「·」、「×」两侧的空格和「14–27」里的连接号 → 匹配到的行直接采用白板稿原文。
- 行首「−」号和行尾被误读的字丢失 → 匹配范围向两端扩展到未匹配的识别字符。
- 中文逗号后空隙过大：生图对全角标点做了挤压 → 逐字实测挤压量。
- 「+92.3%」一类大数字：原图是宋体数字配小一号「%」，还原成了黑体、同字号 → 数字字体跟随同色同字号的中文行，行尾单位单独设字号。
- 标题下方残留笔画尖：修补相邻文字行时，裁切边距把上一行的遮罩也带进来重修了一遍 → 每组只修补自己的遮罩。

对 74 页提案里最难的 6 页做回归：识别文字与原交付一致，色差变化在 ±0.9 以内。

## 四、1.0.0：改名与四项规则（2026-09-25）

使用者提出的修改：

1. 改名 Doc-image-deck，中文名「文图方案」；源码、前因后果和 README 放在一个包里。
2. 白板稿生成后增加一个环节：去掉标题和短句的句号，只保留详细描述和大段文字后的句号。
3. 白板稿先给使用者确认，确认后才开始生图。
4. 生图采用三个完全不同的视觉方向；在本地目录里查找视觉参考并询问使用者，有好的参考就作为其中一个方向；使用者只给一张时，另外两个方向自行设计。
5. 以 MIT 许可发布到 GitHub。

实现与验证：

| 要求 | 实现 | 验证 |
|---|---|---|
| 标点整理 | `punct.py`，`deck whiteboard` 生成前自动执行；按位置和长度决定去留，列表结尾的「；」一并处理；改动记入 `标点整理.md`，列出句号不统一的列表 | 测试稿：标题、短结论、短要点去掉句号；50 字说明段、两句的段落保留；混排列表被列出 |
| 白板稿先确认 | `deck approve` 把上屏文字的摘要写进 `project.json`；`deck prompts` 每次核对，未确认或确认后改过字都拒绝运行 | 未确认 → 拒绝；确认后改标题 → 拒绝；只改版面建议 → 仍有效 |
| 本地查找参考并询问 | `deck refs` 扫描项目目录、上级目录、原文档目录，按关键词和尺寸排序，生成候选清单和编号缩略图；`--export` 把选定的图片、PDF 页、PPTX 页导出为参考图 | 测试目录：6 个候选排序正确，Logo 被排除，同目录 8 张图收为 3 张；PDF、PNG、PPTX 导出均成功 |
| 三个完全不同的方向 | `direction.json` 增加 `dims`（五项维度）、`imagery_mode`（配图方式）、`source` 与 `refs`；`deck directions` 检查两两不同并生成对比表；按参考建立的方向在样张和全量生图时自动附参考图 | 字段缺失、配色相同、配图方式相同都被拦下；实际附 2 张参考图生成 1 页，107 秒 |

真实生图测试时发现，模型会照着参考图在一句没有句号的结论后面加上句号。为此在提示词里写明不得自行加句号，并在文字核对里增加 `PUNCT` 状态；重新生成后该页核对通过。

## 五、1.1.0：去 AI 味、Windows 支持与生图模型调研（2026-09-25）

使用者提出的修改：

1. 文档转成白板稿之前，增加一道 humanizer-zh 工序，去掉 AI 腔。
2. 兼容 Windows，2024 年以后的版本即可。
3. 研究生图能否改用 ChatGPT 网页版，以用上 Images 2.5，而不是 Codex 内置的旧版。

实现与验证：

| 要求 | 实现 | 验证 |
|---|---|---|
| 去 AI 味 | 大纲写好后，把上屏文字与讲稿导出为带编号标记的 Markdown，按 humanizer-zh 编辑后导入。导入核对标记、数字、英文和引号内文字，不一致就拒绝写回；没处理完不能生成白板稿；用户后来改的字可以只导出改动条目，用户指定的原话可以直接确认 | 测试稿：故意改动要点里的一个数字，导入被拦下；改正后写回 2 条；改标题后只导出这 1 条；确认原话后白板稿正常生成 |
| Windows | 平台差异集中到一个模块：Windows 上文字识别用 RapidOCR（PP-OCRv6），PDF 用 pypdfium2，PowerPoint 走 COM，字体为当前用户安装，思源宋体按字重生成静态字体、名称与 Mac 上一致；命令入口、安装、环境检查全部改成 Python，zsh 脚本不再需要 | 在 Mac 上用 Windows 的识别与渲染路径跑 4 页可编辑还原：32 条文案逐字一致，色差 7.76、12.96、5.29、4.85，Apple Vision 路径为 8.04、13.34、5.91、5.52；静态字体名称核对无误。COM 驱动、字体注册、目录联接和 `deck.cmd` 要在 Windows 上跑过 CI 或实机才算验证 |
| 生图模型 | 调研后不采用网页版自动化 | 见下 |

生图模型的调研结论：

- Codex CLI 0.155 的内置 `image_gen` 在客户端写死了 `model: "gpt-image-2"`（源码 `codex-rs/ext/image-generation/src/tool.rs`），配置项和命令行都不能换模型。
- OpenAI 2026-09-08 发布 Images 2.5，公告称面向 ChatGPT、ChatGPT Work 和 Codex 用户开放；服务端实际用哪一版，从客户端和图片元数据都看不出来。
- API 里有 `gpt-image-2.5-flare`（默认推荐）和 `gpt-image-2.5-sunburst`（编辑精度更高、更慢），质量档新增 xhigh、max，需要 API Key、按 token 计费。
- 用程序驱动 chatgpt.com 生成并下载图片，违反 OpenAI 使用条款中不得自动抓取输出的规定，还会遇到人机验证和页面改版，不采用。
- 可选的后续做法：在管线里加一个 API 后端，显式指定 2.5，并用同一套提示词和文字核对做 A/B 比较；或者提供人工到网页版出图、再导入的半自动流程。

## 六、1.2.0：逐页视觉规划、品牌调研与安装说明（2026-09-25）

使用者提出三项修改：生图要避免模板化；设计方向之前先做品牌 VI 与 Logo 调研；分别为 Claude Code 和 Codex 写安装说明。第一项用一份 15 页的执行规划端到端测试，后两项根据测试中的经验补上。

### 逐页视觉规划

使用者在之前的实践中发现，整页生图的结果模板化、重复性强：多数内容页都是「标题 + 几张卡片」，图示看不出内容之间的关系。提出的修改：生图环节要针对分拆后每一页的语义做分析，给出明确的提示词，让每一页既保持全稿风格统一，又有变化，图示清楚、有逻辑。

原因有两个：

1. 提示词里只有逐字文案和一句版面建议，模型不知道文字之间是先后、回流、收窄还是对比，只能退回默认版式。
2. 全量生图时每页都附同一张样张作风格参考，参考说明只写了「不照搬具体版式」，模型仍然大量沿用样张的构图。

实现：

| 改动 | 做法 |
|---|---|
| 逐页视觉规划 | `outline.json` 每页写 `visual`：这一页要说清什么、信息结构（14 种）、画法、唯一的视觉焦点、构图骨架（10 种）、配图母题；正文块可写 `visual`，把文字绑定到图中的某个部分 |
| 检查 | `deck visual`：规划缺项、相邻两页骨架相同、同一骨架超过内容页四分之一、「并列要点」超过五分之一时不通过；`project.json` 可限定页数和不设章节页。`deck whiteboard` 生成后自动检查，`deck prompts` 不通过就拒绝运行 |
| 提示词 | 风格系统写成全稿统一，构图和图示写成逐页变化；写入本页视觉规划、前后两页的骨架，以及图示规则（箭头、分组、大小对应文字里的关系，代表数字的形状按比例）；带 `visual` 的正文块分组列出文字 |
| 参考图说明 | 附图只提供风格，不照搬构图、图示类型和配图题材 |

用一份 15 页的执行规划端到端测试（封面、13 页内容、封底，不设章节页）：

- 视觉规划：13 页内容页用了 8 种构图骨架、9 种信息结构，同一骨架最多 3 页（整幅图示）。
- 三个方向各出 2 张样张，6 张全部一次成功，每张 115–145 秒。
- 全量 15 页一次成功，每张 121–142 秒。对照联系表：13 页内容页都按规划的骨架和图示落地，相邻页没有雷同。
- 新旧提示词对照：同一方向、同一组版面建议，用改动前的提示词重生成 5 页。旧提示词出现的问题：P03 画成三个分开的漏斗，断点数据挤在底部；P05 各泳道各画各的图标，还多出货车、购物车；P06 自行加了 01–06 编号；P13 没有画版面建议要求的矩形树图，画成了树状列表。新提示词这 5 页都按规划画出：连续收窄的漏斗、贯穿三条泳道的路径、突出交接节点的闭环、按金额比例的矩形树图。两组都用了按规划写的版面建议，所以这组对照只衡量提示词本身，不包括逐页规划这一步的作用。

测试中发现并修正的问题：

- 文字核对误报：图示节点窄，一句话常折成 3–4 行，OCR 的行序又在几栏之间交错，原来只拼接相邻两行，15 页里有 4 页误报 MISS。现在按位置把同一栏里上下相接的行拼起来匹配，误报消失。
- 模型会把画法说明里的词（「内容端」「每周」）画成标签，还会自行算出百分比写在比例条上。提示词改为明确只写引号里的文字；references 要求画法说明里不出现上屏文字以外的标签词。
- 脚注两次落进左下角的 Logo 预留区。提示词增加脚注位置要求后仍然落进去，改版面建议、把脚注放进结论横栏右端后才通过。
- 候选对照图被一张竖长的设计系统图撑高了整行；Logo 路径原来按当前目录解析。均已修正。

可编辑还原：274 行文字可编辑，缺失 0 行；与图文版逐页平均色差全稿均值 8.11，最高三页为 9.74–12.46。首轮有 4 处要返修：
- 封面渐变色标题的颜色取成了背景色，改为留在底图；
- 3 组「大号数字 + 小号单位」的 KPI（「310 万元」「约 250 条」「约 30 万元」）叠字，并把「约」识别成繁体「約」。

切分点只能解决其中一部分。原因有两个：OCR 行框不含左侧的小字「约」，落在框外的切分点无效；切出单字「条」时切分不成立。这 3 组最后放进排除区，留在底图。另外，排除区要完整包住 OCR 行框才生效，第一次框得太紧没有生效。这些都写进了 references。

### 品牌调研

测试中三个方向都是在没看客户品牌 VI 的情况下设计的；Logo 也是到选完方向才处理，而客户只有反白版，要临时生成浅底用版本。1.2.0 把这两件事前移到设计方向之前：

| 改动 | 做法 |
|---|---|
| 索取材料 | 确认点 1 同时向用户索取品牌手册、Logo（彩色版与反白版）、往期物料和截图 |
| 调研 | `deck brand init` 生成六节模板；阅读客户材料（PDF、PPTX 导出为图片），联网检索官网、旗舰店和官方账号，写品牌色色值、Logo 版本、字体与版式、视觉风格与禁忌、对三个方向的约束 |
| 门槛 | `deck brand check` 与 `deck directions` 检查六节齐全、品牌色有色值、资料来源有文件或网址；每个方向必填 `brand_fit` |
| Logo | `deck logo` 把测试中手工做的联合 Logo 固定下来：去底色、补齐深浅两版、按面积平衡拼接、写入 `project.json`。用测试的两个 Logo 验证，结果与手工版一致 |

Codex 只有以 `--search` 启动才有联网检索，这一点写进了 SKILL.md 和 Codex 安装说明。

### 安装说明

README 的安装一节改为两个客户端各一段摘要，完整说明放在 `docs/install-claude.md` 和 `docs/install-codex.md`。两份说明都按同一结构写：适用范围、前提、安装、验证、开始使用、更新、卸载。末尾是给 agent 的逐条步骤，每一步写明命令和预期结果，并规定 agent 不替用户登录账号。命令和参数（`codex login status`、`--search`、`-s danger-full-access`）都在本机 Codex CLI 0.155 上核对过。

### 1.2.1：第二版测试中的修正

使用者看过第一版后提出：视觉偏塑胶、偏立体，希望做成商务与科技杂志的编辑风，扁平、精致、有纸质印刷质感，信息密度更高；这一轮由 agent 自行选方向并做完。于是在同一份文档上走了一遍 1.2.0 的完整流程：

1. 联网检索品牌公开资料，并读取 Logo 源文件。官网和网店都没有公开标准色，主色取客户文档画板的深海军蓝，强调色取 Logo 上的三个圆点色。
2. 每页文字按原文和画板补充，上屏文字从 2,093 字增加到 3,104 字。
3. 出三个扁平编辑风方向，三个方向各用一个圆点色作强调色。agent 按四条标准评估后选定「科技季刊 · 纸本信息图」：是否符合要求、信息密的页是否清楚、图示是否清楚、生成文字的准确率。

全量 15 页一次成功，2 页返修；可编辑版 364 行文字可编辑，逐页平均色差均值 9.22。发现并修正的问题：

| 问题 | 修正 |
|---|---|
| 时间轴上阶段名在上、日期在下，OCR 的行序在五栏之间交错，三个方向的样张都误报 MISS | 同一栏上下相接的两行也拼起来匹配 |
| 封面不加页码，提示词仍要求页码角留空，文字核对也把封面落款报成 CORNER | 按页判断是否加页码，只在有页码的页预留这个角 |
| 这套方向的粗黑体标题比思源黑体窄，可编辑版靠约 −20% 的字距对齐宽度，相邻字叠在一起 | 字距最紧到字号的 −6%，其余缩小字号；标题清晰，文字高度略小 |

## 七、2.0.0：大流程不变，细化分页、方向与质检（2026-09-26）

使用者提出：五个阶段和两个确认点不动，研究中间环节还能怎么细化，重点是设计方向和分页；在 GitHub 上调研同类项目，从其他 skill 里借鉴做法；改完之后自己找小文件做生图对比测试，评估、再迭代一轮，把流程跑通。

### 调研

复盘 1.2.x 的两次 15 页测试，并读了 14 个 GitHub 同类项目的源文件（整页生图做幻灯片、图片转可编辑 PPTX、大纲与分页三类）、本机 11 个 PPT 与设计类 skill，以及金字塔原理、横向与纵向逻辑、ghost deck、演讲稿与阅读稿之分等写作方法。复盘发现的问题：

| 问题 | 证据 | 原因 |
|---|---|---|
| 三个方向构图相同 | 两次测试 6 张封面都是「左侧标题、右侧产品切面」；有一个方向声明「纯图形、不用照片」，封面仍是三维产品 | 封面的版面建议和配图建议写在大纲里，三个方向共用；方向检查只比较文字描述 |
| 字量规则没有执行，也不分页型 | 第二版测试 6 页正文超过 150 字（最多 226 字），没有提示；这些页首轮文字核对全部通过 | 规则只写在文档里；全稿统一一个数 |
| 规划外的图标 | 第二版测试 13 页内容页里 8 页出现与内容无关的线描图标，其中 3 个在可编辑还原时被识别成文字 | 方向描述写了 pictograms；没有配图建议时默认写「最多小线描图标」 |
| 风格漂移靠人工发现 | 第二版返修 2 页，其中 1 页是标题位置和其他页不一致 | 没有自动检查 |
| 大数字配单位切不开 | 两次测试共 7 组留在底图，都是人工处理 | 可编辑还原不知道哪些行是 `kpis` 块 |

借鉴的做法和出处：按读法定页数与字量（ppt-master、frontend-slides、guizang-ppt-skill）；按版式限定字段字数（gpt-image2-ppt-skills、codex-ppt-skill、baoyu-slide-deck）；原文出处限定为真实存在的章节（PPTAgent）；每页一个目的、同一事实不跨页重复、禁止描述稿子本身（presenton）；风格维度用固定选项组合（baoyu-slide-deck）；按页面角色匹配参考图（gpt-image2-ppt-skills、banana-slides）；局部改字只改错字区域（gpt-image2-ppt-skills）；审图与问题分级（banana-slides、ppt-master、anthropic pptx）；先扩文本框再缩字号（knight-imagetopptx-skill）。没有采用：固定的风格预设库（绕开品牌调研）、只出一张样张直接当终稿（三方向对比是大节点）、平面拟合去字（本流程页面多有纸纹）、图标抠成独立对象（依赖大，默认已不画图标）。

### 实现

| 环节 | 改动 |
|---|---|
| 分页 | 故事线先于正文（`deck storyline`：章节、原文出处与覆盖、首尾页、跨页数据）；`deck_mode` 分阅读稿和演讲稿；按构图骨架和读法的每页容量；演讲稿节奏检查；目录、执行摘要、附录页型 |
| 设计方向 | 方向自带封面构图与主体；`axes` 固定选项比较（含图示语言、配色策略）；行业常见款与 `temperature`；图标策略默认不画；默认禁画常见生成外观 |
| 质检 | `EXTRA`、`DRIFT`；`deck fix` 局部改字；`deck audit` 子 agent 审图；可选的按骨架配参考图和角落定位图 |
| 可编辑还原 | `kpis` 大数字自动切分；超大数字留在底图；粗笔画大字的背景色估计；标题先向右延伸再缩字号 |

### 验证

- 单元测试 63 项；冒烟测试在 Apple Vision 和 RapidOCR + pypdfium2 两条路径上都通过。
- 文字核对：用第二版测试的 15 张生图跑新的 `textcheck`，`EXTRA`、`DRIFT` 没有误报；用第一版测试的生图跑，查出了当时靠人工发现的「内容端」标签。调试中发现并修正：OCR 行高不能用来比较标题字号（同样大小的标题框高相差 ±20%），改为量标题笔画的实际高度；只按子序列匹配会把「内容端」算成已有文字，改为只认连续匹配，单个认错的字（「滞」读成「滯」）按前后字放行。
- 可编辑还原回归：用新代码重跑第二版测试的 15 页，不再手工圈大数字。结果是 373 行可编辑（原 364 行），留在底图 13 处（原 16 处），逐页平均色差均值 9.49（原 9.22，原稿把 4 组大数字留在底图，色差自然更低）；没有大数字的页与原结果相差不超过 0.2，只有 1 页因标题保持原字号而高 0.9，肉眼看不出差别。调试中试过两种做法后放弃：用平面颜色加噪点填超大数字的去字区域，出现明显的颗粒光晕；把所有高于页高 18% 的行留在底图，封面标题也变得不可编辑，改为只处理以数字为主的行。标题向右延伸起初也作用于正文行，使同一段的字号不一，改为只用于标题级的行。
- 新文档测试（一份 1,743 字的内部方法文档，演讲稿，12 页正文 + 1 页附录）：故事线与容量检查通过；3 个方向样张的封面构图互不相同，内容样张的图示语言各不相同，没有规划外的图标；多出文字检查拦下了照片封面里模型自行写在笔记本和便签上的手写字；木刻方向在 `avoid` 写了 robots 的情况下仍画了两个机器人头盔人形。后两个问题当即改进提示词：默认禁画代表 AI 的机器人形象，图片里的纸张、便签、屏幕不出现可读文字。

| 问题 | 原因 | 修正 |

## 八、几个关键决定

- **生图走 Codex 内置 `image_gen`，不走 Images API**：用 ChatGPT 套餐额度，不产生 API 费用；`imagegen.py` 先确认 Codex 以 ChatGPT 账号登录，否则停止。
- **Logo 和页码不交给模型**：模型画的 Logo 不准确，也无法事后替换；作为独立对象叠加后，图文版和可编辑版都能直接改。
- **白板稿是唯一的文字来源**：生图提示词逐字取自白板稿，可编辑还原也以它为准校正识别结果。确认点 1 之后再改字，要重新生成对应页，所以确认用脚本强制，不靠 agent 自觉。
- **方向差异用硬性检查**：早期测试里三个方向的封面都是同一类产品静物，差别只在配色；现在五项维度和配图方式都必须不同。
- **方向建立在品牌调研上**：先读客户材料、查品牌公开资料，再定方向；调研用脚本检查是否填完，不靠 agent 自觉。
- **版式变化来自逐页语义**：不给模型「多样化」这类笼统要求，而是逐页写清信息结构和画法，并用相邻页骨架检查兜底。
- **先定故事线再写正文**：标题串读和原文出处先过脚本检查，正文写好后再调结构代价大，也容易漏掉原文章节。
- **字量按用途和构图定**：同样两百字，在阅读稿的整幅图示页上没有增加错字，在演讲稿的大字页上就太多；一个全稿统一的数管不住两头。
- **封面构图属于方向，不属于大纲**：大纲只写这一页要说什么；封面怎么构图由方向决定，否则三个方向只能换配色。
- **图标默认不画**：模型的默认习惯是给每个要点配线描图标，既让页面模板化，又给可编辑还原添加识别错误。
- **运行环境与 skill 文件分开**：运行环境放在 `~/.local/share/doc-image-deck`，两个宿主共用；skill 目录只有规程和脚本。
- **以 PowerPoint 的渲染为准**：PDF 导出、比对和排版标定都用本机 PowerPoint，交付给客户的也是这个渲染结果。1.0.0 只支持 macOS；1.1.0 起支持 Windows，平台差异集中在 `scripts/hostos.py`，其余代码两个平台共用。

## 九、已知限制

- 生图宋体的字面比思源宋体宽，PowerPoint 不能横向拉宽文字，字形只能做到接近。
- 纸纹、烫金等质感复杂的页面，可编辑版与图文版的色差偏高（测试中最高约 13–15）。
- 截图、海报、表情包里的文字需要人工圈定为排除区，留在底图上。
- 完整链路（生图 → 合成 → 可编辑）用 4 页和 15 页测过；74 页规模只验证过可编辑还原这一段。
- 大数字配前缀、单位的自动切分只用于白板稿 `kpis` 块里的数值；外来稿件和不在 `kpis` 块里的大小字混排仍要手工切分或留在底图。高于页高 18% 的超大数字留在底图。
- 演讲稿的每页容量是初始值，只在一份 13 页演讲稿上用过。
- `--skeleton-refs` 在一次 13 页对比中没有看出差别；`--corner-guide` 还没有做对比测试。
- 品牌调研的检查只核对是否填写和格式，调研内容是否准确要靠人看。
- Windows 上的 PowerPoint COM 驱动、字体注册、标定规律，以及 LaMa 在 CPU 上的耗时，需要在 Windows 实机上验证；CI 的 Windows 机器没有 PowerPoint，只能覆盖其余部分。
