# 阶段 1 · 白板稿与 outline.json

白板稿是整条流水线的文字来源：生图提示词逐字取自这里，可编辑还原阶段也以这里的文字为准校正识别结果。所以白板稿的文字就是终稿文字，必须写到能直接对客户使用。

写 `outline.json` 分两步：先写故事线（每页标题、所属章节、原文来源），`deck storyline` 通过后再写正文和视觉规划。

## 故事线

先定这套稿要让观众接受哪一个结论，再定用哪几章、每章几页去支撑它。正文写好后再调结构，改动大、容易漏掉原文章节，也容易把一个判断摊成好几页。

### 步骤

1. 通读原文，写 `storyline.thesis`：全稿一句话结论。写不出来，说明原文还没有结论，先和用户确认。
2. 定论证方式 `storyline.mode`：
   - `scqa`：情境—冲突—问题—答案，适合提案、诊断。
   - `chronological`：按时间推进，适合执行规划、复盘。
   - `report`：按事项汇报，适合周报、月报。
3. 定读法和页数：`project.json` 的 `deck_mode`（`present` 演讲稿 / `read` 阅读稿），见下文「读法与页数」。
4. 分章：全稿 3–7 章，同一章的页连续。每页写 `chapter`；内容页的 `kicker` 一般就写章节名。
5. 逐页只写 `kind`、`chapter`、`title`（结论式标题，写判断，不写栏目名）、`visual.message`、`source`。
6. 原文里不上屏的章节写进 `storyline.dropped`，每条写理由。
7. 运行 `deck storyline <项目>`，读 `故事线.md` 的标题串读：只读标题，能不能连成一个完整的论证；执行摘要的要点是否与后面各章一一对应。

### 字段

| 字段 | 位置 | 说明 |
|---|---|---|
| `storyline.thesis` | 顶层 | 全稿一句话结论，必填 |
| `storyline.mode` | 顶层 | `scqa`、`chronological`、`report` |
| `storyline.dropped` | 顶层 | `[{"source": "原文标题", "reason": "不上屏的理由"}]` |
| `chapter` | 每页 | 所属章节；内容页和附录页必填 |
| `source` | 每页 | 这一页来自原文的哪一节、哪张表图，如 `["2.1 渠道现状", "表3"]`；原文没有、由用户或其他材料补充的写 `"补充：<出处>"`；原文所在目录里的图片、画板可以写文件名 |
| `covers` | 执行摘要页 | 要点依次对应的章节名，顺序与章节一致 |

`project.json` 的 `source` 是 Markdown 或 .docx 时，`deck storyline` 读出原文的标题和正文做核对；PDF、PPTX 等读不出标题的原文，只检查结构，来源与覆盖检查跳过。

### 检查

`deck storyline <项目>`（`deck whiteboard` 和 `deck prompts` 也会运行，不通过时拒绝）：

- 不通过：
  - 缺 `thesis`；内容页或附录页没有 `chapter`；同一章分成了不相邻的几段。
  - 原文可读时，内容页没有 `source`；`source` 在原文的标题、正文和同目录文件里都找不到。
  - 原文的一、二级标题既没有对应的页，也不在 `dropped` 里；`dropped` 没写理由。
  - 附录页不在封底之后，或不连续；正文写了「附录 A3」而没有这一页。
  - 封底标题是「谢谢」「Thank you」「Q&A」；标题里写「本页」「本章」「我们将」「接下来」这类描述稿子本身的话。
  - 目录页没列全章节；执行摘要的 `covers` 顺序与章节不一致或缺章。
  - 同一指标（`kpis` 的说明相同）在不同页数值不同。
- 提示：
  - 6 页以上的稿子不是 3–7 章。
  - 阅读稿 8 页以上没有执行摘要。
  - 演讲稿的内容页数落在「时长 ÷ 2」到「时长 ÷ 1.5」之外。
  - 一个原文小节展开到 4 页以上。
  - 相邻两页来源相同、正文合计不超过一页的容量（合并候选）。
  - 标题与原文小标题相同，或以「概述」「介绍」「现状」「分析」结尾（像栏目名）。
  - 正文里有描述稿子本身的过渡语。
  - 同一事实在执行摘要以外的两页重复出现。

`00_白板稿/故事线.md` 列出：全稿结论、读法与页数、按章节分组的标题、标题连起来读的一段、逐页原文来源、原文以外的补充、原文各标题用在哪几页、不上屏的原文和检查结果。确认点 1 把它放在第一项给用户。

### 读法与页数

| | `present` 演讲稿 | `read` 阅读稿 |
|---|---|---|
| 用途 | 现场讲，讲者在场 | 发给对方自己看，页面要脱离讲者也能看懂 |
| 每页 | 一个观点，要点不超过 3 条，细节写进讲稿 | 页面自足，可以有依据和明细 |
| 页数 | 内容页约「时长 ÷ 2」到「时长 ÷ 1.5」（约 1.5–2 分钟一页，只作检查，不作目标） | 按原文信息量，明细多时放附录 |
| 节奏 | 连续高密度页不超过 3 页，8 页以上至少一页低密度页 | 不限制 |
| 超出容量 | 细节移进讲稿 | 明细移进附录页 |

用途混合时不取中间值：主要用于现场说服的按演讲稿，主要用于会后传阅的按阅读稿。页数上限 `max_pages` 只算正文，附录不计；结构页（封面、目录、章节页、封底）和内容页分开算。

### 拆页与合页

- `message` 里有两个独立的判断：拆成两页。
- 相邻两页的 `message` 是同一个判断：合成一页。
- 正文超过这页骨架的容量：换容量更大的骨架，或拆成续页；演讲稿把细节移进讲稿，阅读稿把明细移进附录页。
- 正文里和标题无关的内容删掉（纵向逻辑：页内每一块都要支撑标题）。
- 同一事实只放一页；执行摘要可以重复后文的结论。

## outline.json 结构

```json
{
  "title": "秋季新品上市整合营销方案",
  "storyline": {
    "thesis": "上市首月把预算集中在搜索承接，让新品进入用户的搜索框",
    "mode": "scqa",
    "dropped": [{"source": "附录：历史活动清单", "reason": "与本期决策无关，客户已有"}]
  },
  "pages": [
    {
      "id": "p01",
      "kind": "cover",
      "tone": "dark",
      "kicker": "2026 年 9 月",
      "title": "让新品在上市首月进入用户的搜索框",
      "subtitle": "秋季新品上市整合营销方案",
      "blocks": [{"type": "text", "text": "小红书 × 抖音 × 门店 × 会员"}],
      "layout_hint": "标题左对齐占左侧 45%，右侧放产品特写，留出大面积留白",
      "image_hint": "新品杯饮置于浅色石材台面，侧逆光，浅景深",
      "notes": "开场说明本次方案的范围与时间"
    },
    {
      "id": "p02",
      "kind": "content",
      "chapter": "问题诊断",
      "source": ["2.1 内容表现", "表3"],
      "kicker": "问题诊断",
      "title": "内容量翻倍，平均互动却下降一半",
      "blocks": [
        {"type": "kpis", "items": [{"value": "+96%", "label": "近 90 天笔记量"}, {"value": "−48%", "label": "篇均互动"}]},
        {"type": "bullets", "items": ["七成参与达人粉丝不足 1,000", "高互动笔记集中在 1 万–10 万粉的腰部达人"]}
      ],
      "takeaway": "问题不在投入不够，而在铺量稀释了内容效率",
      "footnote": "数据来源：平台后台，近 90 天",
      "layout_hint": "左侧两个大数字，右侧两条要点；底部一条结论横栏",
      "image_hint": "无照片，右上角一条下行的细线趋势图",
      "visual": {
        "message": "笔记量涨了近一倍，篇均互动却掉了一半，投入越多效率越低",
        "structure": "compare",
        "form": "两根并排的粗柱：左柱向上（+96%），右柱向下（−48%），柱长按百分比比例；两柱之间一条细线连接，表示同一时期",
        "focal": "向下的 −48% 柱与数字",
        "skeleton": "bignum",
        "motif": "无照片，柱形本身就是主图"
      },
      "notes": "…"
    }
  ]
}
```
### 页面字段

| 字段 | 说明 |
|---|---|
| `id` | `p01`、`p02` … 与页序一致 |
| `kind` | `cover` 封面 / `agenda` 目录 / `summary` 执行摘要 / `section` 章节页 / `content` 内容页 / `closing` 封底 / `appendix` 附录（放在封底之后，页码 A1、A2） |
| `chapter` | 所属章节，见上文「故事线」 |
| `source` | 原文来源，见上文「故事线」 |
| `tone` | `light` / `dark`；不写时由设计方向的 `tone` 规则决定 |
| `kicker` | 标题上方的小标签（章节名、栏目名），可省略 |
| `title` | 结论式标题，一句话说清这一页的判断 |
| `subtitle` | 副标题，可省略 |
| `blocks` | 正文块，按阅读顺序排列，类型见下表 |
| `takeaway` | 页底结论句，可省略 |
| `footnote` | 数据来源等脚注，可省略 |
| `layout_hint` | 版面建议：信息怎么分区、谁大谁小、图放哪里。直接进入生图提示词 |
| `image_hint` | 配图建议：主体、构图、光线。没有配图写「无照片」及可用的图形元素 |
| `visual` | 视觉规划：这一页要说清什么、信息结构、画法、视觉焦点、构图骨架、配图母题，见下文「逐页视觉规划」。直接进入生图提示词 |
| `notes` | 讲稿，写进白板稿和图文版的备注 |

### 正文块类型

| type | 字段 | 用途 |
|---|---|---|
| `bullets` | `items: [str]` | 要点 |
| `steps` | `items: [str]` | 有先后顺序的步骤 |
| `numbered` | `items: [{label, title, text}]` | 编号条目（01 / 02 …），带小标题和说明 |
| `kpis` | `items: [{value, label}]` | 大数字 |
| `table` | `caption, header: [str], rows: [[str]]` | 表格，不超过 6 行 × 5 列 |
| `columns` | `columns: [{title, items: [str]}]` | 并列分栏（对比、分类） |
| `quote` / `callout` | `text, source` | 引语 / 强调框 |
| `text` | `text` | 一段文字 |
| `heading` | `text` | 正文里的小标题 |

任何正文块都可以加 `"visual": "这一块画成什么"`（如「漏斗第二段的标签和人数」），把这块的文字绑定到图中的某个部分。提示词按块分组列出文字，模型更容易把文字放到对的图形上。

## 写作要求

1. 文字遵守宿主的写作规范（如用户全局指令里的中文写作规范）。结论先行，标题即观点。
2. 字量上限按构图骨架和读法定，见下文「每页容量」；标题不超过 30 字，内容页的 `kicker` 不超过 8 字，单条要点不超过 40 字。超出就换骨架、拆续页，或把明细移进讲稿或附录。
3. 数字、单位、专有名词写成最终形式（「1 万–10 万粉」「61.72%」「会员日 3.0」），生图会逐字照搬。
4. `layout_hint` 写具体的空间安排，不写形容词堆砌。好的例子：「左 40% 放标题和三条要点，右 60% 放一张满高照片，底部一条结论横栏」。`layout_hint` 管分区，`visual.form` 管图示怎么画，两者不要互相矛盾。
5. `image_hint` 逐页区分题材，全稿不重复；不要求画 Logo、真实人物肖像（除非用户提供了参考图并确认可用）、手机截图或 App 界面，这些由后期贴入。
6. 需要贴真实截图的页，在 `layout_hint` 里写「右侧 50% 留空，后期贴入截图」，并在阶段 3 之后手工贴入。

## 每页容量

`deck visual` 按每页的构图骨架和 `deck_mode` 检查两个数：正文汉字数（不含 `kicker`、标题、副标题）和上屏文字条数（每一段单独上屏的文字算一条，含标题和 `kicker`；表格单元格不计条数，按行列数限制）。

| 骨架 | 演讲稿：正文汉字 / 条数 | 阅读稿：正文汉字 / 条数 |
|---|---|---|
| `hero` 满版主视觉 | 40 / 5 | 80 / 12 |
| `bignum` 大数字 | 60 / 8 | 120 / 12（另可加一张表） |
| `split`、`asym` | 100 / 10 | 190 / 25 |
| `cards` 并列卡片 | 100 / 10 | 190 / 16 |
| `diagram`、`bands`、`radial`、`quadrant` | 120 / 14 | 250 / 28 |
| `table` 表格 | 120 / — | 250 / — |

表格不超过 6 行 × 5 列（不含表头）。阅读稿的数值取自 2026-09 一次 15 页阅读稿测试：各骨架实测的最大字量再上浮约 10%，这些页首轮文字核对全部通过；在扁平编辑风下，每页两百多字、二十多条文字没有增加错字，所以阅读稿的上限主要管可读性。演讲稿的数值是初始值，按「一页一个观点、细节进讲稿」定，还没有测试数据。

## 逐页视觉规划

生图模型如果只拿到标题、几条文字和一句版面建议，大多会退回「标题 + 三张卡片」一类的默认版式，整套稿看起来一页一个样板。所以写每页文字的同时，要分析这一页在说什么、文字之间是什么关系，据此写出 `visual`，给模型一个明确的画法。

### 字段

| 字段 | 内容 | 写法 |
|---|---|---|
| `message` | 观众看完这一页要明白的一件事 | 一句话，通常是标题的判断加上最关键的依据 |
| `structure` | 信息结构：文字之间的关系 | 从下文「信息结构与常用画法」选一个 |
| `form` | 画法：用什么图形、几个、朝哪个方向，箭头代表什么，哪些形状按数值比例，哪段文字放在哪个图形上 | 具体到照着就能画 |
| `focal` | 视觉焦点：全页最大、最醒目、唯一使用强调色的元素 | 只写一个 |
| `skeleton` | 构图骨架 | 从下文「构图骨架」选一个 |
| `motif` | 配图或图形母题，可省略 | 与本页内容直接相关的物件或场景，全稿不重复 |

`message`、`structure`、`form`、`focal`、`skeleton` 每页必填，封面和封底也要写（通常是 `claim` + `hero`）。视觉规划不属于上屏文字，改它不影响白板稿确认。

### 分析步骤

1. 写 `message`：读完整页文字，写出观众要看懂的那件事。写不出来，说明这一页信息太杂，考虑拆页或删减。
2. 判断 `structure`：看文字之间的关系。有先后是流程或时间轴，逐级减少是漏斗，结果回到起点是闭环，一个整体拆成几部分是层级或构成，几方放在一起比较是对比，按两个维度归类是矩阵，各方各管一块是分工。要点之间确实平行、没有上述关系时，才用「并列要点」。
3. 写 `form`：同一种结构有多种画法（见下表），按本页的文字量和数据选一种，写清图形元素和文字的对应关系。不写图标；只有图标本身表达内容时（如勾与叉表示做与不做）才写，并写明它代表什么。有数字时，图形大小按数值比例画（预算占比、各阶段金额、人数）。多块文字对应图中不同部分时，在正文块上加 `visual`。`form` 和正文块 `visual` 里不要出现上屏文字以外的标签词（如「内容端」「每周」）和算出来的数字（如百分比）：模型会把它们画到页面上。需要这类标签时，把它写进正文，按改字流程重新确认。
4. 定 `focal`：通常是标题判断所依据的那个元素，如最关键的数字、断点、结论所在的节点。
5. 选 `skeleton`，再对照前后页：相邻两页骨架不同；同一种骨架不超过内容页的四分之一（至少允许 2 页）；字量要在这种骨架的容量以内（见「每页容量」）。演讲稿还要看节奏：hero、bignum 且正文不超过上限一半的页算低密度页，连续高密度页不超过 3 页。
6. 写 `motif`：按选定方向的配图方式呈现；阶段 2 选定方向后复核一次，改成适合该方向的题材。

### 信息结构与常用画法

| `structure` | 关系 | 常用画法 |
|---|---|---|
| `claim` 单一论断 | 一句判断 | 超大字号标题 + 一张主视觉，大面积留白 |
| `kpi` 关键数字 | 数字本身就是论据 | 超大数字 + 比例条、环形进度或前后对比柱 |
| `compare` 对比 | 两方或多方比较 | 左右同构对照、对照表、前后对比 |
| `flow` 流程 / 链路 | 有先后 | 横向节点 + 箭头、折线路径、泳道流程 |
| `loop` 闭环 / 回流 | 结果回到起点 | 环形图、带回流虚线的流程 |
| `funnel` 漏斗 / 收窄 | 逐级减少 | 漏斗、逐级收窄的横条、标出断点缺口 |
| `timeline` 时间轴 / 阶段 | 按时间分阶段 | 横向时间轴、甘特条、阶梯 |
| `hierarchy` 层级 / 分解 | 整体拆成部分 | 树状图、金字塔、嵌套方块 |
| `composition` 构成 / 占比 | 部分占整体的比例 | 堆叠条、环形图、矩形树图、华夫格 |
| `matrix` 矩阵 / 分类 | 按两个维度归类 | 2 × 2 象限、分类矩阵 |
| `layers` 分层 / 梯度 | 由内到外或由上到下的层次 | 同心圆、横向色带、阶梯 |
| `roles` 分工 / 泳道 | 各方职责 | 双栏或多条泳道、责任矩阵 |
| `checklist` 清单 / 待办 | 事项 + 负责人 + 时间 | 勾选清单、日历卡片 |
| `list` 并列要点 | 真正平行的几点 | 编号卡片；全稿不超过内容页的五分之一（至少允许 1 页） |

### 构图骨架

| `skeleton` | 说明 |
|---|---|
| `hero` 满版主视觉 | 一张主视觉或超大字占满画面，文字很少 |
| `split` 左右分屏 | 左右两块（约 4:6 或 5:5），一侧文字、一侧图示或图片 |
| `diagram` 整幅图示 | 标题在上，一幅宽图示占三分之二以上面积 |
| `cards` 并列卡片 | 3–4 张等宽卡片或分栏 |
| `bignum` 大数字 | 1–3 个超大数字主导，配一个辅助图形 |
| `table` 表格 | 表格或单元格矩阵主导 |
| `bands` 横向分层 | 自上而下的横向色带，一层一条 |
| `radial` 中心放射 | 中心一个元素，其余围绕或排成环 |
| `asym` 非对称 | 一大块图 + 一条窄文字栏 |
| `quadrant` 四象限 | 2 × 2 四格 |

### 统一与变化

全稿统一的是设计方向决定的风格系统：底色、配色、字体与字重、标题位置与字号、边距、线条与图标样式、配图调色。逐页变化的是构图骨架、图示类型、焦点元素的大小、配图主体与景别。需要节奏时，可以把一两页关键结论页设为深色（页面 `tone: dark`），深色内容页不超过内容页的四分之一。提示词会同时写明这两部分，并告诉模型前后两页用的骨架，要求本页与之不同。

### 页数与章节页

用户限定页数或不要章节页时，写进 `project.json`：`"max_pages": 15` 限定正文页数（含封面、封底，不含附录），`"section_pages": false` 表示不设章节页，章节名写进内容页的 `kicker`。`deck visual` 会检查这两项。

### 检查

`deck visual <项目>` 检查视觉规划并写 `00_白板稿/视觉规划.md`（逐页规划表、构图节奏、密度节奏、每页字数与条数及上限、骨架使用次数）。不通过的情况：缺字段或取值不在表内；相邻两页骨架相同；某种骨架超过内容页的四分之一；「并列要点」超过内容页的五分之一；超出 `max_pages`；`section_pages` 为 false 却有章节页；超出骨架容量、表格超过 6 × 5、标题超过 30 字；演讲稿连续 4 页以上高密度页，或 8 页以上没有低密度页。相邻两页信息结构相同、两页画法或母题文字相同、内容页正文不足 20 字（合并候选）时给出提示。`deck whiteboard` 生成白板稿后自动检查并报告；`deck prompts` 在检查不通过时拒绝生成提示词。

## 去 AI 味

`outline.json` 写好之后、生成白板稿之前，用 humanizer-zh（[op7418/Humanizer-zh](https://github.com/op7418/Humanizer-zh)，MIT）处理全部上屏文字和讲稿。`project.json` 的 `"humanizer"` 可以换成其他同类 skill 的目录名。

1. `deck humanize <项目> export`：把含中文的上屏文字和每页讲稿写进 `00_白板稿/文案_原稿.md`，每条一行 `⟦p02.03 要点⟧ 文字`，讲稿可以多行；同时打印 humanizer-zh 的 SKILL.md 位置。
2. 按 humanizer-zh 的规则编辑这份文件，另存为同目录的 `文案_改后.md`。标记不改、不删、不新增；标题、要点、表格保持简短；数字、英文、品牌与产品名、引号和书名号里的文字不动；原文没有的信息不补。
3. `deck humanize <项目> import`：核对后写回 `outline.json`。拒绝写回的情况：标记缺少或多出；某条的数字、英文、引号内文字有变化；上屏文字出现换行；导出之后 `outline.json` 又被改过。上屏文字变长超过四分之一时给出提示。确认改动无误可加 `--force`。
4. 改动逐条追加到 `00_白板稿/去AI味记录.md`；处理过的文字记在 `去AI味_已处理.json`。`deck whiteboard` 发现有未处理的文字会拒绝运行。
5. 后续改字：`deck humanize <项目> export --changed` 只导出改过或新增的条目；用户给定原话、不需要处理的，用 `deck humanize <项目> accept --note "说明"` 记为已处理。`deck humanize <项目> status` 列出未处理的条目。

去 AI 味只改表达。导入核对拦得住数字、英文、引文的变化，拦不住意思的偏移，所以确认点 1 给用户时附上改了几条，用户可以对照 `去AI味记录.md`。

## 标点整理

`deck whiteboard` 在生成白板稿之前自动执行（`--no-punct` 跳过），也可以单独运行 `deck punct <项目>`（改动后会重新生成白板稿）。规则：

| 位置 | 处理 |
|---|---|
| 全稿标题、`kicker`、`title`、`subtitle`、正文小标题、表格标题 / 表头 / 单元格、大数字及说明、编号条目小标题、分栏标题、引语出处 | 去掉结尾句号 |
| 要点、步骤、分栏条目、页底结论、脚注 | 单句且不足 40 字的去掉句号；40 字及以上的详细描述保留 |
| `text` 段落、引语、强调框、编号条目说明 | 单句且不足 30 字的去掉句号；30 字及以上保留 |
| 含两句及以上的文字（句中有 。！？） | 保留句号 |
| 列表条目结尾的「；」 | 与句号同样处理，避免「A；B；C」去掉句号后结尾不一致 |
| 讲稿、版面建议、配图建议 | 不处理 |

阈值可在 `project.json` 里改：`"punct": {"long_chars": 40, "desc_chars": 30, "keep": ["要原样保留的句子"]}`。每次改动追加到 `00_白板稿/标点整理.md`；同一列表里有的条目保留句号、有的没有时，记录里会列出「列表内句号不统一」，改写成同一长度层级，或把要保留的句子写进 `keep`。

`deck punct <项目> --check` 只检查不修改，`deck approve` 前会自动做这项检查。生图提示词要求模型不得在没有句号的文字后面自行加句号，`deck textcheck` 用 `PUNCT` 标出生图里多出句号的页。

## 确认点 1

白板稿生成后必须先交给用户确认，确认前不做设计方向和生图。给用户的内容：`故事线.md`（全稿结论、标题串读、不上屏的原文和原文以外的补充，放在第一项）、白板稿 PPTX 路径、页数、逐页标题、标点整理改了几处、`视觉规划.md` 的构图节奏；同时附上 `deck refs` 找到的视觉参考候选，询问用户是否有想用的参考（见 `02_设计方向与生图.md`）。

用户确认后运行 `deck approve <项目> --note "<用户意见摘要>"`，确认记录写进 `project.json` 的 `approval.whiteboard`，其中 `signature` 是全部上屏文字的摘要。`deck prompts` 每次运行都会核对：没有确认记录、或确认后上屏文字有改动，都会拒绝生成提示词。只改 `layout_hint`、`image_hint`、`visual`、`notes` 不影响确认。`deck approve --status` 查看当前状态。

## 命令

`$S/deck whiteboard <项目>` → 检查故事线 → 核对去 AI 味已完成 → 标点整理，然后生成 `00_白板稿/<name>_白板稿_<suffix>.pptx` 与 `outline.md`，再检查视觉规划、写 `视觉规划.md`。字体为微软雅黑（中文）与 Arial（英文数字），每页按内容量在 11–18 pt 间自动选字号，章节与来源、视觉规划、版面建议、配图建议、明暗和讲稿写在备注里；附录页右下角标 A1、A2。
